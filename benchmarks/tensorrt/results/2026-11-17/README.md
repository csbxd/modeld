# 4080 SUPER：TensorRT 与 TensorRT-RTX 对比

2026-11-17 在 s8030 的 RTX 4080 SUPER（32 GiB 显存）实测。对这个模型和当前资源配置，**继续采用 TensorRT-RTX 更合适：1080p GPU 管线吞吐约高 25%，额外显存约低 36%；普通版缓存 plan 后的上下文准备更快。样本中的画质指标基本一致。**

## 配置与范围

- RIFE 4.26 Heavy，原始 packed FP32 ONNX；同一份权重、输入字节、CUDA 13.4、驱动 620.70.06。
- TensorRT-RTX 1.7.1.116，对比普通 TensorRT 11.4.0.106。
- FP32、关闭 TF32、`NVIDIA_TF32_OVERRIDE=0`、工作区 4 GiB、0 条辅助流、两个执行上下文和独立 CUDA Graph。
- 原生 1920×1080 与 1280×720，没有缩放。每个后端/尺寸使用两个缓存进程、六轮计时；单流延迟各 600 次采样。
- 正式 modeld 服务保持运行。基线的进程监测包含 381 个 modeld 样本，没有检测到它执行 GPU 计算。显存报告是测试进程初始化后的额外设备分配，包含引擎、双上下文、Graph 与输入输出缓冲。
- RGB 测试输入由 asa 的 FFmpeg 8.1.3 转换一次，然后将同一字节流传给两种后端。公开样本和各文件校验和见 [samples.json](samples.json)、[rgb-sha256.txt](rgb-sha256.txt)。

## 稳态速度与显存

| 项目 | TensorRT-RTX | 普通 TensorRT |
|---|---:|---:|
| 1080p 单流延迟中位数 | 18.070 ms | 21.189 ms |
| 1080p 单流延迟 P95 | 18.137 ms | 21.239 ms |
| 1080p 双流纯推理吞吐 | 58.02 新帧/s | 46.71 新帧/s |
| 1080p 完整 GPU 管线吞吐 | **57.45 新帧/s** | 46.09 新帧/s |
| 1080p 管线六轮范围 | 57.33–57.61 | 46.08–46.10 |
| 1080p 额外显存 | **2100 MiB** | 3284 MiB |
| 720p 单流延迟中位数 | 8.861 ms | 9.374 ms |
| 720p 双流纯推理吞吐 | 123.91 新帧/s | 106.44 新帧/s |
| 720p 完整 GPU 管线吞吐 | **123.67 新帧/s** | 107.42 新帧/s |
| 720p 额外显存 | **1018 MiB** | 1502 MiB |

完整 GPU 管线包含两张 RGB 图片上传、输入预处理、模型推理和 NV12 转换。它**不包含 CPU 解码、NVENC 编码、音视频同步和网络传输**，因此不能直接当作 mpv 端到端帧率。

原始每轮数据在 [performance](performance)，汇总脚本输出在 [summary.json](summary.json)。时钟、温度和功耗记录在 [gpu.csv](gpu.csv)，后台进程检查见 [process-gpu.log](process-gpu.log)。

## 编译与准备时间

| 1080p 项目 | TensorRT-RTX | 普通 TensorRT |
|---|---:|---:|
| 没有测试 plan 时生成引擎 | **0.716 s** | 24.600 s |
| 首轮双上下文、预热及 Graph 准备 | 6.610 s | **1.000 s** |
| 缓存 plan 后双上下文、预热及 Graph 准备 | 6.462 s | **1.101 s** |

构建与 GPU 准备分开计时；这些数字不是完整程序启动时间，也不代表清空操作系统及所有编译缓存后的全冷启动。当前实现持久化 plan，未额外接入 RTX 专用的 runtime-cache API。

普通 TensorRT 的 1080p 引擎还测试了构建优化等级 5：构建花费 89.699 秒，缓存进程的 GPU 管线吞吐为 **46.19 新帧/s**，没有改变排名。18 份 1080p 输出与默认等级 3 的输出逐字节相同。补充数据见 [optimization-level-5](optimization-level-5)、[quality-opt5-summary.json](quality-opt5-summary.json) 及浮点输出校验和文件。

两套独立安装的 SDK（包括库、头文件与资料）实际占用约 4.44 GiB 与 232 MiB，普通版更大。普通版通过 gentoo-cs 的原生 C++ SDK ebuild 安装在 `/opt/tensorrt`，正式服务继续使用 `/opt/tensorrt-rtx`。

## 数值与画质

5 段 Xiph 实拍测试序列各取两组三帧，在 t=0.25、0.5、0.75 比较，共 30 张预测帧；其中 10 张 t=0.5 输出还与真实中间帧比较。

| 两种后端输出之间 | 最差样本 |
|---|---:|
| RGB PSNR | **91.270 dB** |
| 亮度 SSIM | **0.999999501** |
| 最大样本 MAE，FP32 范围 0–1 | 0.000005857 |
| 最大单通道浮点差 | 0.003808409 |
| 转成 8 位 RGB 后最大通道差 | **1 / 255** |
| 8 位通道值发生变化的最大比例 | 0.1475% |

相对真实中间帧，两种后端的 PSNR 最大差仅 **0.0000240 dB**，SSIM 最大差 **0.000000367**。这组样本没有显示出有意义的画质优劣；差异主要是浮点计算与舍入层面的差别。这里只比较了同一个模型的两个运行后端，不能据此评价 RIFE 相对其他插帧算法的优劣。

跨后端 PSNR/SSIM 与相对真实中间帧的指标含义不同；上述 91 dB 是两个后端互相比较的数值一致性，**不是**模型相对真实中间帧的重建 PSNR。完整逐样本数据见 [quality.json](quality.json)。SSIM 使用 11×11 高斯窗口、sigma=1.5、BT.709 全范围亮度；解析解自测也已通过。

## 对实时播放的含义

精确的 30→60 fps 每秒需要生成 30 张新帧，两种后端都有 GPU 计算余量。精确的 24→60 fps 约需 48 张新帧，RTX 的 GPU 管线在此预算上仍有余量，普通版的这组配置不足。23.976→60 等不整齐对齐的时基可能需要接近 60 次推理/秒，原生完整 1080p Heavy FP32 就比较紧张，不能只依据输出标注 60 fps 判断能否持续实时。

这些判断只涵盖当前版本、模型、输入和同等资源限制。解码、编码及网络仍会减少余量；没有把本次吞吐数字当作所有片源的端到端实时保证。
